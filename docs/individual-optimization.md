# 個別項目の測定・改善

状態: 個別評価を継続中。全項目高評価の条件は未達です。
品質ゲートの基準を維持し、測定した一部を全参照機能の同等性と扱いません。
横断的な新規アプリケーション性能試験へ進む条件は、引き続き
`python scripts/check_quality.py --gate` の成功です。

## 追加した測定と改善

127ケースを追加しました。スタイル46、入力・フォーカス37、純粋なプロトコル41、
収集CLI 3です。各ケースに31サンプルと改善前後の全出力検査があります。
単一macOS arm64上で順番に実行し、コンパイル・Miri・カバレッジ計測と性能測定を
重ねていません。CPU周波数・affinityは固定しておらず、常駐メモリは未測定です。

| 対象 | 中央値の改善前 → 改善後 | 割り当て等の注意 |
| --- | --- | --- |
| RGBからANSI256の代表色 | 483.53 → 13.15 ns | 最短二乗RGB距離と先頭優先tieを維持 |
| フォーカスID 1,024個・全て異なる | 865,527.50 → 95,225.84 ns | 累積要求バイト58,186 → 133,474、一時索引の費用を含む |
| フォーカスID 3個・全て異なる | 184.42 → 145.38 ns | 4回・117要求バイトで同じ |
| Sixel 80×24・16色 | 29,785.00 → 14,820.84 ns | 711 → 9回、9,568 → 5,870要求バイト |
| Kitty RGB 1×1 | 517.50 → 297.50 ns | 3 → 2回、146 → 96要求バイト |
| Spinnerの単純な借用表示12種 | 3.23–3.38 → 1.47–1.55 ns | 双方0割り当て。既存84ケース内の再測定 |

これらはRust内の改善前後比較です。x/ansiの色変換はHSLuvの判定を使い、
ANSI先頭16色の扱いも異なります。同じ出力ポリシーではないためGoとの倍率は
掲載しません。RGB全16,777,216入力のANSI256変換を独立した全palette探索と照合し、
一致しました。ANSI16について全RGB検証を実行したという意味ではありません。

少数IDが遅かった索引の初版・中間版、空集合の2.08 → 3.58 ns、1,024重複IDの
26,787.50 → 26,837.50 nsも保存しています。Ratatui収集CLIの中間版に対するp95悪化、
変更していない経路の揺らぎも削除していません。

## 正しさ・証拠の改善

- Unicode非対応モードで全角文字を`?`へ置き換える際、2セル目の背景色・反転属性が
  欠けていました。同じstyleの空白で元のセル幅を満たし、書き込み途中の失敗後も
  次のフレームで画面を復旧します。色なし・truecolor、右端・消去・cursorを独立した
  端末状態モデルで再生しました。不正な旧出力に対する速度倍率は出しません。
- 品質対象の列挙を固定フォルダからGitの追跡・未追跡・非ignoreファイル全体へ変更。
  ルートのbuild.rsや将来のbenchesが漏れる失敗を再現し、回帰試験で防止しました。
- 測定記録では重複ID、NaN/Inf、負値、不足サンプル、出力・意味・反復回数の不一致を
  拒否します。Python最適化モードでも同じ失敗になります。
- 収集CLIの古い実行ファイルによる無効測定は別名で保存しました。
  有効な結果からは除外し、現在の測定器はコミット済みソースとreleaseビルド成功を
  必須とします。詳細はADR 0027にあります。

## 未完了と進行条件

86プログラム・40評価単位のうち56評価軸が75未満のままです。
性能28（うち完全未測定12、部分測定16）、参照元一致18、動作5、外部ツールの移植性5です。
新しい証拠で6評価単位の性能を0から50へ更新しましたが、全体を高評価にはしていません。
完全未測定なのはANSI直接経路、端末ライフサイクル／モード／Unix signal、facade、
examples、Go収集ツールと一部のPython収集・解析・検証・報告プログラムです。
各単位の残件は[明示台帳](quality-plan.json)に記録しています。

全宣言・platform/feature条件、未対応機能、同一意味の参照元比較、常駐メモリ、
実際のタイマー／端末入力、故障注入なども残ります。既存84ケースの参照元比較は
回帰確認として再実行しますが、新規の全フレームワーク評価の開始とは扱いません。

全項目高評価の後に、入力から更新・購読／effect・layout・render・端末出力までの
横断最適化へ進みます。その段階でMatea自身の評価と参照元フレームワークとの比較を
別の試験群として設計・実行します。F5および画像エンジン／CUDAは引き続き未承認です。

Spinnerの借用経路はインライン化し、所有文字列を作るラベル処理を私有関数へ分けました。
追加の5件のMiriでラベル、共有フレーム、時刻、購読経路を確認しました。
再測定では同じ実行ファイルでもキー照合等の極小処理が2–6ns程度に変動しました。
[順序を反転した同一実行ファイルの再測定](evidence/optimization/spinner/repeat-context.json)も保存し、
観測された全ての悪化をコード変更の効果と断定しません。
これらの経路は長いbatchや測定条件の再検討を含め、性能評価の残件です。
